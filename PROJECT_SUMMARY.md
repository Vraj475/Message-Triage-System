# Customer Message Triage System — Full Implementation Blueprint

This document contains the exact, detailed specifications of the AI Customer Message Triage System as built. You can provide this to any developer or AI as a complete, comprehensive blueprint of the system's architecture, dependencies, data flow, and edge case handling.

## 1. Tech Stack & Environment
- **Backend:** Node.js 20+, Express 4, Mongoose 8. 
  - *Key Packages:* `@google/generative-ai`, `joi`, `cors`, `dotenv`.
  - Runs on Port `5000`.
- **Frontend:** React 18, Vite, React Router DOM 6, Axios, Bootstrap 5.
  - Runs on Port `5173`, proxies `/api` to `localhost:5000`.
- **Database:** MongoDB running locally on `27017`, database name: `triage_system`.

## 2. Environment Configuration (`backend/.env`)
```env
PORT=5000
MONGODB_URI=mongodb://127.0.0.1:27017/triage_system
GEMINI_API_KEY=your_api_key_here
GEMINI_MODEL=gemini-2.0-flash-lite
AI_PROVIDER=mock # Options: gemini, mock, openrouter
```

## 3. Data Models (Decoupled Architecture)
To avoid monolithic documents and bypasses of Mongoose `save` hooks, the schema is explicitly decoupled:

### 3.1 `Dataset` (`backend/models/Dataset.js`)
Groups batched message uploads.
- `name` (String, required)
- `messageCount` (Number, default 0)

### 3.2 `Message` (`backend/models/Message.js`)
Stores raw, untrusted customer input.
- `datasetId` (ObjectId, ref: Dataset)
- `rawText` (String, default: '')
- `normalizedText` (String, required)
- `status` (Enum: `['pending', 'completed', 'failed']`)

### 3.3 `TriageResult` (`backend/models/TriageResult.js`)
Stores the output generated by the AI (or the mock provider).
- `messageId` (ObjectId, ref: Message)
- `category` (String, Enum: `billing`, `technical`, `complaint`, `refund`, `account`, `inquiry`, `spam`, `unclear`, `unknown`)
- `priority` (String, Enum: `P0`, `P1`, `P2`, `P3`)
- `summary` (String), `suggestedAction` (String)
- `needsHuman` (Boolean), `confidence` (Number 0.0 - 1.0)
- `reviewStatus` (Enum: `auto_accepted`, `needs_review`, `failed`)
- `validationStatus` (Enum: `valid`, `repaired`, `invalid`)
- `isApiFailure` (Boolean) - Flags if the fallback was hit due to rate limits.
- `rawModelOutput` (String, select: false)

### 3.4 `HumanReview` (`backend/models/HumanReview.js`)
Ground-truth evaluations supplied by support staff.
- `messageId` (ObjectId), `datasetId` (ObjectId)
- `category` (String), `priority` (String), `needsHuman` (Boolean)

### 3.5 `EvaluationRun` (`backend/models/EvaluationRun.js`)
Point-in-time metrics generated by comparing `TriageResult` to `HumanReview`.
- Stores `overallAgreementRate`, `categoryAgreementRate`, `priorityAgreementRate`, `escalationAgreementRate`.
- Stores a `confusionMatrix` mapping expected vs actual categories.

## 4. API Endpoints

- **`GET /api/health/database`**: Safely masks the URI credentials and returns collection sizes.
- **`GET /api/health/ai`**: Returns configuration state (`configured: true/false`, `provider: 'gemini' | 'mock' | 'openrouter'`).
- **`GET /api/configuration`**: Returns `constants.js` categories and prompt settings.
- **`POST /api/datasets/paste`**: Ingests array of text strings. Validated via `Joi.string().allow('')`.
- **`POST /api/triage/message/:id`**: Triages a single message via the active AI provider.
- **`POST /api/triage/batch/:datasetId`**: Finds all `pending` and `failed` messages in the dataset and triages them sequentially.
- **`POST /api/reviews/:messageId`**: Saves human ground-truth.
- **`POST /api/evaluation/run/:datasetId`**: Aggregates human reviews vs AI results and saves to `EvaluationRun`.

## 5. Core AI Logic (`backend/services/triageService.js`)

### 5.1 Pre-filtering
Instantly flags empty strings, single characters, or random keyboard smashing as `isGarbage=true`, assigning `category: 'unclear'` without spending API tokens.

### 5.2 Prompt Injection & Rules
The system prompt strictly commands the AI to never follow instructions inside the customer message.
**Conflict Resolution:** If a message contains both a refund and a billing issue, the rules dictate prioritizing "refund". 

### 5.3 Auto-Repair
The `validateTriageJSON` function actively repairs common LLM output mistakes:
- Strips ` ```json ` fences.
- Maps invalid priorities (e.g. `p1`) to standard `P1`.
- Maps hallucinated categories to `unknown`.
- If the JSON is fatally broken, marks `validationStatus: 'invalid'`.

### 5.4 Mock Provider & Safe Fallback
- If `AI_PROVIDER=mock`, the system intercepts the request and deterministically returns local JSON to bypass API limits and test UI flows (supports `charged twice` -> billing, `ignore previous instructions` -> spam).
- If the real AI API hits a rate limit (`429`), it retries up to 3 times. If all fail, it returns a `safeFallback` object:
  `{ category: 'unclear', priority: 'P3', needs_human: true, isApiFailure: true }`.

## 6. Frontend UI Implementations

### 6.1 Triage Table (`TriageTable.jsx`)
- Differentiates visual states: 
  - **Completed**: AI succeeded, standard category/priority badges.
  - **Processing Failed**: `isApiFailure` is true. Shown as a red badge, clearly instructing the user to retry.
- Displays detailed validation metrics, tokens used, latency, and whether the AI output was "Repaired" in an expandable detail modal.

### 6.2 Dashboard (`Dashboard.jsx`)
- Dataset-aware UI. Allows switching between dataset batches.
- Progress bar dynamically tracks `pending`, `failed`, and `completed` counts via polling.
- Includes a dedicated "Retry Failed" button.

### 6.3 Evaluation Engine (`EvalReport.jsx`)
- Takes manual human reviews and visualizes exact match rates.
- Renders a multi-colored Bootstrap card grid showing accuracy metrics and the confusion matrix.

## 7. Testing Flow (`backend/tests/flow.test.js`)
Comprehensive test suite asserting:
1. Clear billing texts properly parse to `billing`/`refund` with high confidence.
2. Empty strings trigger the human-review unclear path.
3. Garbage strings trigger the human-review unclear path.
4. Prompt injections do not disclose the system prompt.
5. Missing or failed APIs trigger the `safeFallback` correctly.
6. Batch processors iterate through exactly the remaining `pending/failed` messages.
